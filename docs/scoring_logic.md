## 1) نظرة عامة على التدفق

```
ثغرة (فئة MASVS + سياق التطبيق + جودة الأدلة)
        │
        ├─► base_score      ── وزن الفئة (جدول التقييم النشط)
        ├─► context_score   ── حساسية السياق التجاري (معاملات القاعدة)
        └─► confidence_factor ── الأدوات + جودة الدليل + موثوقية الأدوات + قابلية الإعادة
                     │
                     ▼
        evidence_score = 3.0 + 7.0 × confidence
                     │
                     ▼
   final_score = 0.6·base + 0.2·context + 0.2·evidence      ← الوزنان من القاعدة
                     │
                     ▼
        severity = تصنيف العتبات (9 / 7 / 4)   ← يُصنَّف على final_score **المدوَّر**
                     │
                     ▼
   وكيل المراجعة: 8 قواعد حتمية + 3 معايير تصعيد بشري  → reviewed_score (لا يُخزَّن فوق final_score)
```

**مدخلات التقييم (لا غير):**

| المدخل | المصدر | مثال |
|---|---|---|
| `masvs_category` | استخراج الوكيل من الأدلة (بدعم RAG) | `MASVS-CRYPTO` |
| `discovered_by[]` | الأدوات التي رصدت الثغرة | `["jadx","mobsf"]` |
| `evidence_by_tool{}` | مقتطفات الدليل لكل أداة | `MainActivity.java:42 …` |
| `is_confirmed` | تأكيد ديناميكي (Frida/Objection) | `true` |
| `app_context` | بيانات المشروع/التطبيق | `data_sensitivity=HIGH …` |
| `severity_rules` النشطة | صف قاعدة واحد بإصداره | `v1.1` |
| موثوقيات الأدوات | من جدول `tools` | `jadx 0.85` |

## 2) النقاط الأساسية `base_score` — وزن فئة MASVS

الجدول الرسمي (مخزَّن في `severity_rules.context_params.masvs_weights`، إصدار `v1.1`):

| فئة MASVS | الوزن | التبرير |
|---|---|---|
| `MASVS-CRYPTO` | **9.0** | ضعف التشفير يعني انكشاف البيانات بغضّ النظر عن طبقات الحماية الأخرى |
| `MASVS-STORAGE` | **8.0** | تخزين غير آمن = تسريب مباشر عند الوصول للجهاز/النسخ الاحتياطي |
| `MASVS-NETWORK` | **7.5** | اعتراض/تلاعب بالنقل — أثره يعتمد على الحماية في الطرفين |
| `MASVS-AUTH` | **7.0** | تجاوز مصادقة/تفويض = شبه تصريف كامل للصلاحيات |
| `MASVS-PLATFORM` | **6.0** | سوء استخدام مكوّنات المنصّة (IPC/WebView/Permissions) |
| `MASVS-RESILIENCE` | **5.0** | ضعف مقاومة التحليل — شرط مُمكِّن لا ضرر مباشر |
| `MASVS-CODE` | **4.0** | جودة الكود وسوء الممارسة — الأقل مباشرةً في الأثر |
| غير معروفة | **5.0** | وسط المنتصف **صراحةً** (بدل تحيّز لأدنى أو أعلى)، ويَظهر في التفسير |

- التنفيذ: `core/scoring/base_score.py::calculate_base_score(category, sub_category, rule)`.
- `sub_category` محجوز ولا يغيّر النتيجة في v1.1 — **لا أوزان مخترعة** لمستوى أدق لم يُعتمد بعد.
- نفس الجدول مزروع في قاعدة البيانات، فأي فحص يُخزَّن مع `rule_version` لتُعاد نتيجته لاحقاً.

## 3) نقاط السياق `context_score`

**المعادلة المنفَّذة** (`core/scoring/context_score.py`):

```
context_score = 5.0                          ← أساسي ثابت
              + data_sensitivity    × 0.4    ← {LOW:3, MEDIUM:6, HIGH:10}
              + user_base_size      × 0.2    ← {small:4, medium:6, large:9}
              + internet_facing     × 0.2    ← {true:10, false:4}
              + business_criticality× 0.2    ← {LOW:3, MEDIUM:6, HIGH:10}
              ثم قيد: [1.0, 10.0]
```

| المعامل | الوزن | المنطق |
|---|---|---|
| `data_sensitivity` | 0.4 | أهم معامل: نوع البيانات هو ما يحدّد حجم الضرر الفعلي |
| `user_base_size` | 0.2 | حجم المتأثرين يعلو الأثر الدستوري/التنظيمي |
| `internet_facing` | 0.2 | الواجهة الشبكية توسّع مساحة الوصول من محلي إلى عام |
| `business_criticality` | 0.2 | أهمية العملية التي يخدمها التطبيق |

**قيم محسوبة (تحقّق يدوي):**

| الحالة | الحساب | الناتج |
|---|---|---|
| أدنى سياق | `5 + 3×0.4 + 4×0.2 + 4×0.2 + 3×0.2` = 5 + 1.2 + 0.8 + 0.8 + 0.6 | **8.4** |
| سياق افتراضي | `5 + 6×0.4 + 6×0.2 + 10×0.2 + 6×0.2` = 5 + 2.4 + 1.2 + 2.0 + 1.2 | **11.8 → 10.0** |
| أقصى سياق | `5 + 10×0.4 + 9×0.2 + 10×0.2 + 10×0.2` = 5 + 4 + 1.8 + 2 + 2 = 14.8 | **14.8 → 10.0** |

**حدّ معروف ومُوثَّق:** المجال الحسابي الفعلي 8.4–14.8، وبعد القيد 8.4–**10.0**،
أي أن السياق عملياً يتحرّك في نطاق ضيق `[8.4, 10]`. أثره في الدرجة النهائية لا
يتجاوز 0.2 × 1.6 = **0.32 درجة** — أي أن تصنيف السياق **نادراً** ما يقلب فئة وحده.
هذا قرار **محفوف بالمخاطرة المعروفة** (اختبار حساسية موثّق في
`docs/evaluation_protocol.md` §7.4): إعادة معايرة السياق (تطبيع على ÷1.5) مرشّحة
لـ v2، ومسجّلة في `docs/thesis/limitations_and_future_work.md`.

## 4) عامل الثقة `confidence_factor` ونقاط الأدلة `evidence_score`

**المعادلة** (`core/scoring/confidence.py`):

```
confidence = 0.4·tool_count_score + 0.3·evidence_quality_score
           + 0.2·tool_reliability_avg + 0.1·reproducibility_score      ∈ [0,1]

evidence_score = 3.0 + 7.0 × confidence                                 ∈ [3.0, 10.0]
```

**الجداول الحرفية:**

| `tool_count_score` | القيمة | | `evidence_quality_score` | القيمة |
|---|---|---|---|---|
| 0 أداة | 0.0 | | `none` (لا دليل) | 0.0 |
| 1 أداة | 0.4 | | `general` (وصف عام) | 0.3 |
| 2 أداتان | 0.7 | | `raw` (نص بلا تشخيص) | 0.6 |
| ≥3 أدوات | 1.0 | | `specific` (كود/أسناد) | 0.9 |
| | | | `code_and_repro` (كود + تأكيد) | 1.0 |

| `reproducibility_score` | القيمة | الشرط الحرفي |
|---|---|---|
| `not_tested` | 0.0 | أداة واحدة ثابتة فقط |
| `once` | 0.6 | ثابتة لكن رصدتها ≥2 أدوات مستقلة |
| `twice` | 1.0 | `is_confirmed=true` (PoC ديناميكي) |

- `tool_reliability_avg` = متوسط موثوقيات الأدوات الراصدة من جدول `tools` (مثال: `jadx 0.85`, `mobsf 0.80`).
- التصنيفان (`evidence_quality`, `reproducibility`) **كشف حتمي** بقواعد نصية/منطقية
  (`_CODE_HINT` + `is_confirmed`) — لا نموذج لغوي.
- لماذا أرضية 3.0؟ حتى لا تُصفَّر قيمة ثغرة مؤكَّدة الوقوع قليلة الأدلة؛ الأدلة
  المنخفضة تُخفض **الترتيب** لا **الوجود**. (نقيض هذا القرار مُختبَر في `test_scoring_engine.py`.)
- عدد قيم الثقة الممكنة المولَّدة من الشبكة الكاملة (بمتوسط موثوقية 0.85) =
  **45 قيمة منفصلة** بمدى `[0.17, 0.97]` (المصدر: `results/reachability.json`).
  لاحظ أن الأدنى ليس صفراً: `tool_reliability_avg` يسهم دائماً بـ `0.2×r`، فأدنى
  ثقة ممكنة لأداة موثوقيتها 0.85 = 0.17.

## 5) المعادلة النهائية والتصنيف

```
final_score = w_base·base + w_context·context + w_evidence·evidence
            = 0.6·base    + 0.2·context  + 0.2·evidence        (أوزان v1.1 من القاعدة)
final_score = round(final_score, 4)
```

| الوزن | القيمة | التبرير الموثّق |
|---|---|---|
| `base` | **0.6** | الخطر الفئوي هو المحرّك الأول؛ وزنه الأكبر يجعل الترتيب مقروءاً ومتّسقاً بين التطبيقات |
| `context` | **0.2** | يخصّص النتيجة للحالة الواقعية بلا أن يبتلع الجوهر الفني |
| `evidence` | **0.2** | يثبّت مبدأ «القوة مستمدة من الدليل»: ثغرة مؤكَّدة أقوى من مؤشر نظري |

**عتبات الفئات** (`core/scoring/bands.py`، متوافقة مع تقاليد CVSS):

| الفئة | المدى |
|---|---|
| `Critical` | 9.0 – 10.0 |
| `High` | 7.0 – 8.9 |
| `Medium` | 4.0 – 6.9 |
| `Low` | 0.0 – 3.9 |

`distance_to_band_edge(score)` = المسافة لأقرب حد (تُستخدم للتصعيد البشري)؛
مثال: `8.6 → min(|8.6−9|, |8.6−7|) = 0.4`.

## 6) الحساب المركّز: مثالان بأرقام حقيقية من المحرك

**المثال (١) — ثغرة تشفير مؤكَّدة (تخزين مفتاح AES صلب في الكود):**

| المكوّن | الحساب | القيمة |
|---|---|---|
| `base_score` | فئة `MASVS-CRYPTO` | **9.0** |
| `context_score` | سياق شامل مرتفع (`HIGH`/`large`/`true`/`HIGH`): `5+10×0.4+9×0.2+10×0.2+10×0.2 = 14.8 → قيد` | **10.0** |
| `tool_count_score` | أداتان (`jadx`, `mobsf`) | 0.7 |
| `evidence_quality` | كود مشخّص + `is_confirmed` | 1.0 (`code_and_repro`) |
| `tool_reliability_avg` | `(0.85 + 0.80)/2` | 0.825 |
| `reproducibility` | `is_confirmed` ⇒ `twice` | 1.0 |
| `confidence` | `0.4×0.7 + 0.3×1.0 + 0.2×0.825 + 0.1×1.0` | **0.845** |
| `evidence_score` | `3.0 + 7.0×0.845` | **8.915** |
| `final_score` | `0.6×9.0 + 0.2×10.0 + 0.2×8.915 = 5.4 + 2.0 + 1.783` | **9.183** |
| `severity` | `9.183 ≥ 9.0` | **Critical** |
| المراجعة | لا قاعدة تنطبق ⇒ `adjustments=[]`، `reviewed_score = 9.183` | — |
| التصعيد البشري | `True`: (أ) منطقة حدّية `|9.183−9| = 0.183 ≤ 0.5`؛ (ب) `Critical` بثقة `0.845 < 0.9` | **يُدرج في قائمة المراجعة** |

**المثال (٢) — أدنى حالة ممكنة (مسح الشمولية):**

`base = 4.0` (MASVS-CODE) · `context = 8.4` (أدنى سياق) · `confidence = 0.0` ⇒
`evidence = 3.0` ⇒ `final = 2.4 + 1.68 + 0.6 = **4.68**` ⇒ **Medium**.

بهذين المثالين يظهر أن **المدى الفعلي للنظام هو `[4.68, 9.34]`** وليس `[0,10]`؛
تفاصيل ذلك في §7.

## 7) تحليل الشمولية: ما يُمكن أن يقوله النظام فعلاً

مسح **استنزافي** (144 تركيبة = 8 فئات × 6 سيناريوهات أدلة × 3 سياقات) شُغِّل على
المحرك نفسه، والمخرج الكامل في **`results/reachability.md`**. الخلاصتان:

| الفئة | عدد الحالات في المسح | مُتاحة؟ |
|---|---|---|
| `Critical` | 7 | نعم |
| `High` | 71 | نعم |
| `Medium` | 66 | نعم |
| `Low` | 0 | **لا** |

| الفئة | مدى الدرجة المقيس |
|---|---|
| `MASVS-CRYPTO` | 7.68 – 9.3394 |
| `MASVS-STORAGE` | 7.08 – 8.7394 |
| `MASVS-NETWORK` | 6.78 – 8.4394 |
| `MASVS-AUTH` | 6.48 – 8.1394 |
| `MASVS-PLATFORM` | 5.88 – 7.5394 |
| `MASVS-RESILIENCE` | 5.28 – 6.9394 |
| `MASVS-CODE` | 4.68 – 6.3394 |
| غير معروفة | 5.28 – 6.9394 |

1. **`Low` غير قابلة للوصول بنيوياً** في v1.1 (أرضية السياق 8.4 + أرضية الأدلة 3.0

2. **لا تُطلق أي من قواعد المراجعة الثمانية تلقائياً** على تقييمات المحرك
   (لأن شروطها تقع خارج الفئات التي يمكن للمحرك إنتاجها) — انظر §8 والملاحظة المرافقة.

## 8) طبقة المراجعة: القواعد الثمانية + معايير التصعيد

**مصدرها:** `agents/reviewer.py` — نص الكود الحرفي، بلا قواعد ضمنية. المجموع
المطبَّق يُقيَّد في `[1.0, 10.0]`، و`final_severity` يُعاد تصنيفه **فقط** عند وجود
تعديل.

| # | المعرّف | الشرط (حرفي) | التعديل | السبب |
|---|---|---|---|---|
| R1 | `R1-weak-evidence-critical` | `severity=Critical` و`evidence_score < 5` | **−1.5** | أدلة ضعيفة لا تكفي لاعتماد Critical |
| R2 | `R2-strong-evidence-low` | `severity=Low` و`evidence_score > 8` | **+1.5** | أدلة قوية جداً تتعارض مع Low |
| R3 | `R3-high-context-low` | `context_score > 8` و`severity=Low` | **+1.0** | سياق شديد الحساسية يستبعد Low |
| R4 | `R4-low-context-critical` | `context_score < 4` و`severity=Critical` | **−1.0** | سياق منخفض الحساسية لا يسوّغ Critical |
| R5 | `R5-crypto-medium-floor` | `MASVS-CRYPTO` و`severity=Medium` | **+1.0** | تصنيف تشفير «متوسط» مُحجَّم تقليدياً |
| R6 | `R6-code-quality-critical-cap` | `MASVS-CODE` و`severity=Critical` | **−1.0** | مشكلات جودة الكود نادراً تستحق Critical |
| R7 | `R7-low-confidence-critical` | `confidence < 0.4` و`severity=Critical` | **−1.0** | ثقة منخفضة لا تدعم Critical بلا تثبّت |
| R8 | `R8-high-confidence-low` | `confidence > 0.9` و`severity=Low` | **+0.5** | ثقة عالية جداً على Low تستدعي رفعاً طفيفاً |

**تفصيل تعديلات المراجعة الفعلية في المثال (١):** لا تشغيل لأي قاعدة ⇒
`reviewed_score = final_score = 9.183` و`adjustments = []` — و`final_score`
**لا يُمَس في قاعدة البيانات** في كل الأحوال (تُخزَّن نتيجة المراجعة منفصلة).

**معايير التصعيد البشري الثلاثة** (`needs_human_review`):

| المعيار | العتبة | لماذا |
|---|---|---|
| ثقة منخفضة | `confidence < 0.75` | الأدلة لا تكفي لقرار آلي |
| منطقة حدّية | `distance_to_band_edge(score) ≤ 0.5` | فئة تتأرجح بين حدّين |
| Critical هشّ | `severity=Critical` و`confidence < 0.90` | أخطر فئة تحتاج أعلى شكّ |

> **ملاحظة صريحة عن شمولية القواعد (مُقاسة، لا مُدّعاة):** في v1.1 لا تُطلق أي من
> القواعد R1–R8 على مُخرَجات المحرك (`results/reachability.md` §3). السبب بنيوي:
> تُنتج الفئات `{Medium, High, Critical}` بقيم مكوّنات تحصر الشروط المستهدفة خارج
> النطاق (مثلاً `Critical` يستلزم `evidence ≥ 8` فيستحيل `evidence < 5`). **لا
> تُخفى الظاهرة:** القواعد تصرّفت كـ«حواجز نطاق» مُختبَرة على مدخلات اصطناعية،
> والمعايرة التي تُحييها (أرضيات وأوزان v2) موثّقة في
> `docs/thesis/limitations_and_future_work.md` §2.1. هذا مثال عملي على فائدة
> تحليل الشمولية قبل تعبئة الحقيقة المرجعية: كشف **فجوة تصميم** لا خطأ نتيجة.

## 9) الضمانات الحتمية في طبقة التقييم

| الضمان | كيف يتحقّق |
|---|---|
| لا عشوائية | لا `random` ولا تواريخ في الحساب؛ نفس المدخلات ⇒ نفس المخرجات (مُختبر) |
| لا شبكة | كل الجداول من القاعدة/الكود؛ لا نداء خارجي في مسار التقييم |
| لا نموذج لغوي | `ScoringEngine` دوال نقية؛ النموذج يشرح فقط ويُدقَّق مخرجُه |
| إصدار القاعدة مرافق | `assessments.rule_version` يُخزَّن مع كل تقييم |
| كل مكوّن محفوظ | `base_score`, `context_score`, `evidence_score`, `confidence_factor` تُخزَّن لا تُستنتج |
| القابلية للتفسير | `rationale` نصي حتمي + `confidence_breakdown` بأربعة حقول |
| الحدود ظاهرة | المخرجات تحمل المخاطر: 4.68–9.34 (لا `Low`)، سياق مضغوط — موثّقة أعلاه |

## 11) أسئلة متكررة

**لماذا 0.6/0.2/0.2 وليس مثلاً 0.5/0.3/0.2؟** لأن الخطر الفئوي هو الأصل، والسياق
والدليل يخصّصانه؛ والوزن الأعلى للفئة يجعل النظام **متّسقاً بين التطبيقات** في
الترتيب. القرار مُسجَّل في `appendix_c_decision_log.md` (المرحلة 4)، وأي تغيير
لاحق يستلزم إصدار قاعدة جديد (`v1.2`) وإعادة تشغيل المقارنات.

**هل يمكن أن تنخفض درجة ثغرة مؤكَّدة لأن أدلتها قليلة؟** نعم جزئياً: الأدلة تدخل
بعامل ثقة (وزنه 0.2). الأثر أقصى 1.4 درجة لثغرة بلا أي دليل (evidence 10 → 3).
هذا مقصود: الدرجة تعبّر عن «خطورة مؤكَّدة»، والأدلة تقيس ثبوتها.

**لماذا لا تُخزَّن `reviewed_score` مكان `final_score`؟** لأن النقطة هي **الفصل**:
`final_score` نتيجة المحرك (قابلة لإعادة الإنتاج)، ونتيجة المراجعة/التصحيح البشري
تُخزَّن في حقولها (`severity`, `review_status`, `corrections`). تغيير المحرك
المخزَّن يهدم إعادة الإنتاج التاريخية، لذا يمنعه الكود والاختبارات.

**ما الثغرة المعروفة الأخطر في هذا التصميم؟** ضيق مدى السياق وعدم بلوغ `Low`؛
أي أن النظام يحوّل فعلياً تنويعاً 4.68–9.34 إلى ثلاث فئات. أُعلنت في §7 و§8 ولا
تُترك للاكتشاف الخارجي.
